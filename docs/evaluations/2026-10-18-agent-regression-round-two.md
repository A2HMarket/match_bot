## 新bug与修复

`reply_to_request` 原先把原始引用ID数组限制为6，而工具和提示词允许使用段落编号。例如实际草稿：

```
k2:p2, k2:p3, k2:p7, k6:p4, k6:p5, k7:p5, k7:p6, k8:p7
```

这是4个来源、8个段落，应该只渲染4条链接，却被schema以 refs:too_big 拒绝。另一个亲子草稿7个段落实际只有3个来源。两个真实记录已冻结在 `packages/agent/tests/fixtures/p35-citation-count.json`。

修复按真实产品约束分开计数：

1. 最多6个独立来源/offer；同一k来源的多个段落只计一次。
2. 原始引用ID另设24个上限，限制载荷；同时补上旧代码在合并inline引用后未重新核对独立来源上限的问题，正文引用也不能让7个来源逃逸。
3. 每个段落继续逐一检查是否确实由本轮工具返回。**没有把虚构的k1:p99归并成k1来放行。**
4. 六来源限制从“数组长度”改为按来源编号计数，不是允许更多独立来源。7个来源仍拒绝，已有事实/数字/硬条件/Jev/阶段/审批/频控不变。
5. 工具描述和instructions同步这一单位，AGENT_VERSION递增0.22.0。

先运行失败复现，再修复，新增正反例包括真实8段/4来源只渲染4链接、7来源（包括inline）拒绝、伪造段落拒绝。

**真实续测的证明边界：** 新GP答复使用5个整页ref，没有再次提交大于6的段落数组。因此它证明新版本真实链路能交付有用答复，并不单独证明多段落分支被真实模型触发；该分支的直接证据来自冻结草稿回归。模型检索与用户任务历史也在变化，不能把79,629对111,479的差异宣称为受控A/B的降本比例。
